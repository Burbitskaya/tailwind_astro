## Границы проекта

**Корень проекта:** `D:\Work\tailwind_astro`

- Работать разрешено только с файлами внутри корня проекта.
- Запрещено читать, изменять, удалять или перемещать файлы за пределами проекта,
  включая соседние каталоги в `D:\Work`.
- Запрещены команды, затрагивающие другие каталоги: `cd ..`, операции по родительской
  папке, скрипты с абсолютными путями наружу.
- Проект — отдельный git-репозиторий. Нельзя выполнять команды, которые индексируют
  или меняют файлы родительского репозитория.
- Исключение — системный кэш npm, необходимый для установки зависимостей.
  Исходники вне проекта не изменяются.

### Спрашивать разрешение перед

- установкой, обновлением или удалением зависимостей;
- изменением `package.json`, `astro.config.mjs`, `tsconfig.json`, структуры папок;
- удалением, переименованием или массовым перемещением файлов;
- добавлением фреймворков, интеграций, БД, внешних API и аналитики;
- git-операциями, кроме `git status` и `git diff`;
- любыми действиями за пределами проекта;
- выбором архитектурного варианта или при неоднозначной задаче.

Безопасные локальные изменения можно выполнять сразу, но нужно сообщить о них в итоговом ответе.

## Git

- **`git push` запрещён.** Любая отправка в удалённый репозиторий — только по прямому указанию пользователя.
- Запрещены `git push --force`, удаление веток, тегов и истории.
- Запрещены публикация, деплой, релиз и отправка сайта на хостинг.
- Локальные `git init`, `git add` и `git commit` — только с разрешения пользователя.
- Нельзя перезаписывать чужие изменения и делать `git reset --hard` без согласования.
- Перед коммитом проверять `git status` и `git diff`, чтобы в индекс не попали
  секреты, `.env`, `node_modules`, `dist`, `.astro` и служебные файлы агентов.
- Сообщение коммита — в формате Conventional Commits:
  `feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`, `refactor: ...`.

## Чистый код

- Имена переменных, функций и компонентов объясняют назначение.
- Одна функция — одна ответственность; длинные функции разбиваются.
- Ранние возвраты вместо вложенных `if`.
- Запрещены `any`, небезопасные приведения типов и `@ts-ignore` без причины.
- Типизируются props, состояние и возвращаемые значения.
- Мёртвый код, дубли, отладочные `console.log` и закомментированные блоки удаляются.
- Комментарии объясняют **почему**, а не **что**; очевидный код не комментируется.
- «Магические числа» выносятся в именованные константы.
- Композиция и переиспользуемые компоненты предпочтительнее копирования разметки.
- Не добавлять зависимости ради одной маленькой функции.
- Соблюдать форматирование Prettier и не сортировать классы вручную.
- Не рефакторить код, не связанный с задачей.

## Astro

- По умолчанию — статический HTML и **ноль JavaScript**.
- `.astro` — для статической разметки и контента; React — только для интерактивности.
- `client:load` — осознанно, `client:visible` — для блоков ниже первого экрана,
  `client:only` — только если серверный рендер невозможен.
- Вычисления — во frontmatter или отдельных модулях, не в шаблонах.
- Использовать типизированные `interface Props` и деструктуризацию `Astro.props`.
- Изображения — через `astro:assets` (`<Image />`), а не огромные файлы из `public/`.
- Семантическая разметка: `header`, `nav`, `main`, `section`, `footer`,
  один `h1` на страницу, корректная иерархия заголовков.
- Доступность: `alt`, подписи к полям, `aria-*` по делу, видимый фокус, контраст.
- Не отключать проверки TypeScript и не ослаблять `tsconfig`.
- Файлы в `src/pages/` — маршруты; динамические маршруты — `[slug].astro`.

## Tailwind CSS 4

- Тема и токены — в `@theme` внутри `src/styles/global.css`.
- Не создавать `tailwind.config.js` без необходимости.
- Стилизовать утилитами в разметке; повторяющиеся наборы выносить в компоненты.
- `@apply` — только для глобальных базовых стилей.
- Избегать произвольных значений (`w-[437px]`), если есть шкала Tailwind.
- Mobile-first: базовые классы, затем `sm:`, `md:`, `lg:`, `xl:`.
- Тёмная тема — через `dark:` и системную настройку.
- Порядок классов поддерживает `prettier-plugin-tailwindcss`; вручную не сортировать.
- Не использовать inline-стили для того, что выражается утилитами.

## React

- Только функциональные компоненты и хуки.
- Состояние минимально; производные значения не дублируются в `useState`.
- Обновление состояния — иммутабельно и через функции: `setCount((value) => value + 1)`.
- `useEffect` не используется для вычислений, которые можно сделать при рендере.
- События и списки типизируются; ключи в списках — стабильные `id`.
- Интерактивные элементы — нативные `button`/`a` с корректным `type` и доступным названием.
- Не подключать глобальные сторы и тяжёлые библиотеки без согласования.

## Рабочий процесс и проверки

1. Изучить контекст: прочитать затронутые файлы и существующие соглашения.
2. Спланировать минимальный набор изменений.
3. Менять точечно, не трогая несвязанный код.
4. Проверить результат.
5. Отчитаться: какие файлы изменены, какие решения приняты, что показали проверки.

### Обязательные проверки

```bash
npm run format
npm run lint
npm run check
npm run build
npm run verify
```

`npm run verify` — финальная проверка перед сдачей задачи.

### Dev-сервер

Запускать в фоновом режиме:

```bash
astro dev --background
```

### Безопасность

- Секреты — только в `.env` (не коммитится), не выводить в клиентский код.
- Не логировать персональные данные и токены.
- Внешние ссылки с `target="_blank"` — с `rel="noopener noreferrer"`.
- Пользовательский ввод валидировать на сервере.
- Не добавлять сторонние скрипты без разрешения.
